# Redlet 首版设计基准

基准日期：2026 年 11 月 3 日。适用阶段：完成 Build Your Own Redis 前七章后，开始实现 Redlet 第一版。

首版目标是完成一个运行于 Linux 的 C++ 内存键值服务器，支持约定范围内的 RESP2 命令，并建立可复现的功能与性能基线。后续学习自写哈希表、ZSet、定时器、TTL 和后台任务时，通过明确的模块职责与数据所有权，把修改集中在相关模块。

以下“已确认选型”来自本次讨论；协议与 I/O 正确性约束用于把这些选择落实为可实现的行为。文末的配置数值和局部实现方式尚未确定，不视为已确认选型。本文描述逻辑模块；具体目录与文件划分见[建议目录结构](redlet-directory-structure.md)。

## 已确认选型

| 领域 | 首版设计基准 | 演进约定 |
| --- | --- | --- |
| 运行环境 | C++，Linux 网络接口；开发可在 Linux Dev Container 内进行 | C++ 标准、构建工具及测试框架在实现时固定并记录 |
| 项目组织 | 按职责分目录，首版构建保持简单，产出一个服务程序 | 测试复用实现代码；各模块目录不必分别构建成独立库 |
| 头文件布局 | 同一模块的头文件与源文件放在一起 | 具体文件划分与模块依赖在目录结构设计中细化 |
| 协议 | RESP2 基础命令兼容；普通请求为 bulk string 数组 | 兼容范围落实到命令、语法与实际验证过的客户端用法 |
| I/O 后端 | 直接使用 epoll | 首版不实现 poll 对照后端 |
| 触发模式 | 仅使用 Linux epoll 默认的 LT（水平触发） | 注册事件时使用默认触发模式，保持有限读取批次与主循环调度简单 |
| 线程模型 | 单主线程处理网络、命令和活跃数据库 | 普通 GET、SET 不并行执行；后台销毁等任务待有对应场景后考虑 |
| incoming | 连续缓冲区＋游标 | 容器具体类型待实现；外部使用范围访问，保留以后更换物理布局的余地 |
| 请求参数 | 借用 incoming 内的逻辑字节范围 | 不把接口固定为 std::string_view；参数复制与物理连续性是独立问题 |
| outgoing | 连续缓冲区＋发送游标 | 避免每次部分发送后删除前缀；整理、扩容与容量回收策略可局部调整 |
| 回复生成 | 命令处理器调用具体 ReplyWriter，同步编码并追加到 outgoing | 不建立完整中间 Reply 树；ReplyWriter 不负责 socket 发送 |
| 慢读取连接 | 单连接未发送应用输出设硬上限；追加将超限时关闭连接 | 高低水位暂停和恢复作为条件优化，保留硬上限作为最终边界 |
| 首版键索引 | std::unordered_map，封装在 Database 内部 | 后续学习自写哈希表时替换或对照；不预设自写版本一定更快 |
| 存储访问 | 命令层调用 get_string、set_string、erase 等操作 | 类型判断、修改和条目生命周期由存储模块负责 |
| 调度 | 处理当前有限输入批次中的完整请求，然后交回事件循环 | 每连接命令预算及继续执行队列在压测表明有需要后加入 |
| 优化原则 | 先完成简单正确的首版，再测量、定位并选择优化 | 不为每个候选方向预先建立双实现、虚基类或装饰器体系 |

## 首版命令与兼容范围

| 命令 | 接受的语法与行为 | 正确回复 |
| --- | --- | --- |
| PING | PING，或 PING message | 无参数返回简单字符串 PONG；有参数以 bulk string 返回该消息 |
| GET | GET key；读取字符串 | 存在时返回 bulk string；不存在时返回 RESP2 null bulk string；空字符串与不存在必须区分 |
| SET | SET key value；新建或覆盖字符串 | 成功返回简单字符串 OK；首版不接受附加选项 |
| DEL | DEL key [key ...]；忽略不存在的 key | 返回实际删除的 key 数量；同一个 key 重复出现不能重复计数 |

命令行为依据：[PING](https://redis.io/docs/latest/commands/ping/)、[GET](https://redis.io/docs/latest/commands/get/)、[SET](https://redis.io/docs/latest/commands/set/)、[DEL](https://redis.io/docs/latest/commands/del/)。首版的 SET 是其中的无选项子集。

命令名按 ASCII 大小写不敏感方式识别；key 和 value 保持原始字节。空字符串、零字节、空格和 CRLF 可以作为参数内容，长度按字节计算。不使用 C 字符串终止符判断数据长度。

未知命令、参数数量错误及不支持的 SET 选项，返回明确的 RESP 错误；该命令不修改数据库，连接可以继续处理后面的合法请求。构造错误文本时使用固定文案或经过处理的参数摘要，不能把含任意 CRLF 的客户端内容直接拼进 simple error。

基础互通以实际联调通过的客户端版本和用法为准。redis-cli 的普通 RESP2 命令用法、redis-benchmark 选择的 SET/GET 测试项是首批验证对象。默认 benchmark 套件、inline 请求、管理命令、客户端握手扩展及 CLI 特殊模式不自动纳入兼容承诺。工具若发送未支持的辅助命令，应给出合法错误，再按实际需求决定是否扩展。

第一版只保存内存中的字符串数据。ZSet、TTL、后台销毁属于后续章节演进；持久化、复制、集群、认证、TLS、多数据库切换和淘汰策略未纳入本轮首版范围。

## 模块职责与依赖

| 逻辑模块 | 负责的内容 | 应隔离的细节 |
| --- | --- | --- |
| Server 与配置 | 启动监听、装配各模块、集中管理配置和退出流程 | 不承载各个命令的业务实现 |
| EventLoop 与 epoll 适配 | 注册和修改关注事件、等待就绪事件、分派处理、安排连接清理 | 不理解 RESP 字段、key/value 或数据库容器 |
| Connection 与网络处理 | fd、连接状态、输入输出缓冲、非阻塞读写、事件关注状态 | 不直接操作键索引；不在 read/write 回调里堆放命令语义 |
| Buffer 与 Range | 连续字节存储、读写或消费位置、必要的整理扩容、范围读取与复制 | 不把连续裸指针当作所有上层接口的唯一表示 |
| RESP 请求解析器 | 从有序字节流识别完整请求，生成请求范围和各参数范围 | 不执行命令、不访问数据库、不直接关闭 socket |
| 命令处理器 | 识别命令、验证参数、调用数据库操作、调用 ReplyWriter | 不获取 unordered_map 迭代器、桶或内部条目来自行修改 |
| Database | 键查找、字符串读写、删除、类型规则和数据所有权 | 不依赖 fd、epoll、Connection 或 RESP 格式 |
| ReplyWriter | 把回复类型编码到输出缓冲，遵守追加预算并报告失败 | 不发送 socket，不持有数据库引用等待异步发送 |

这些职责可以由少量具体类和函数完成，不要求每个模块对应独立库、抽象基类或继承层次。数据库操作返回状态及必要的数据引用，不等于重新引入协议层的 Reply 树。

普通请求的路径为：网络读取 → 输入缓冲 → RESP 解析 → 命令处理 → Database 操作 → ReplyWriter 编码 → 输出缓冲 → 网络发送。错误状态沿调用路径交回连接管理逻辑处理。

## 字节流与请求解析

RESP2 普通命令使用数组结构和带长度的 bulk string。请求边界及参数边界由解析器确定；一次 read、一次 TCP 收包或单个换行都不能作为完整命令的依据。bulk payload 按声明长度读取，其内容可以包含 CRLF。[RESP 协议规范](https://redis.io/docs/latest/develop/reference/protocol-spec/)

首版接受的命令参数必须是实际的 bulk string 字节串；null bulk string、null array、嵌套数组等不属于接受的命令输入形态。它们进入明确的不支持或协议错误路径，不能因负长度而一直停留在 NeedMore。回复端支持 null bulk string，不代表请求端接受它作为普通命令参数。

解析至少区分三种结果：

| 结果 | 含义 | 调用方行为 |
| --- | --- | --- |
| Complete | 一条完整请求已解析，参数范围和已消费字节数可用 | 同步执行并编码回复，再消费对应输入范围 |
| NeedMore | 当前数据是尚未完整的请求前缀 | 保留必要输入及解析状态，等待更多数据 |
| Invalid | 字段格式、终止符、长度或范围违反约定 | 停止解析该连接，进入协议错误清理路径 |

解析元数据要能表示整条请求的范围，以及每个参数的范围；命令处理器不再重复拆解 RESP。参数描述本身可以分配或复用少量内存，借用设计不代表零分配。

长度数字、参数数量、累计请求长度、偏移与长度相加都要检查上限和整数溢出。检查应发生在大块分配或越界访问之前。非法长度不得被当作永久的 NeedMore。实际限额集中配置，具体数值在实现时记录。

半包支持是首版正确性要求。解析器是否保存更细的扫描状态、是否存在可优化的重复解析，属于实现和后续测量问题；不能把“当前一定会重复扫描”当作既定事实。

## 数据所有权与借用有效期

| 数据 | 持有者 | 借用与生命周期约束 |
| --- | --- | --- |
| incoming 字节 | Connection 的输入缓冲 | 请求解析和执行期间不能覆盖、回收或使相关范围失效 |
| 请求及参数范围 | 解析结果或连接的解析状态 | 描述位置而不拥有参数字节；必须关联正确的输入来源与位置语义 |
| 数据库 key/value | Database | 生命周期独立于连接；SET 完成后不能仍依赖 incoming 的存储 |
| GET 的数据引用 | Database 持有，当前调用临时借用 | 仅用于本次同步访问与回复编码，不跨后续修改或异步任务保留 |
| outgoing 回复字节 | Connection 的输出缓冲 | 保存至成功交给内核或连接清理；与原请求、数据库 value 分离 |
| ReplyWriter | 当前同步调用中的编码对象 | 借用输出目标；成功完成编码后不再依赖输入 value 的引用 |

首版连续缓冲可以使用偏移量表示范围。偏移量不会自动解决有效期：消费前缀、整理、扩容和复用空间时，仍要维护坐标及字节身份。半包解析状态尤其不能保存追加数据后已经失效的裸指针。

处理一条完整命令时，先保持参数范围有效，完成 Database 操作和 ReplyWriter 编码，再允许消费或整理它引用的输入。无需等待 socket 把回复全部发出后才消费请求。

SET 需要让数据库获得长期拥有的 key/value；在当前借用方案下通常会发生入库复制。GET 经 ReplyWriter 写入 outgoing 时也通常会复制 value。该设计减少中间表示，不承诺全链路零拷贝。

## 事件循环与读写推进

监听 socket 和连接 socket 使用非阻塞模式。使用 Linux epoll 默认的 LT，在有限读取批次内取得数据，处理当前缓冲中能够完成的请求，然后回到外层循环。不能把有限批次悄悄变成对一个持续活跃连接无限地“读入并执行”。

同一连接内按请求顺序执行并编码回复；不同连接的处理顺序由事件循环调度，不提供跨连接的全局到达顺序。pipeline 支持包括正确处理同一次读取中的多条请求以及跨多次读取的一条请求。[教程 6.6](https://build-your-own.org/redis/06b_event_loop_more)

网络处理遵守以下规则：

- read/recv 返回正数时追加实际字节；EAGAIN 或 EWOULDBLOCK 表示暂时不能继续读取；EINTR 按既定策略重试；返回 0 表示读端 EOF，不等于暂时无数据。

- send/write 返回正数时，只按实际发送数量推进游标；部分发送后保留剩余内容；遇到 EAGAIN 或 EWOULDBLOCK 保留待发送数据，等待后续可写机会；EINTR 按既定策略重试，不推进发送游标。

- outgoing 非空时才需要保留相应的可写处理；清空后撤销无用的 EPOLLOUT 关注，避免 LT 下空转。是否在生成回复后立即尝试一次发送，可在实现中确定并记录。

- 单个连接的关闭由统一路径处理。注销事件、关闭 fd 和释放连接对象必须协调，避免同批事件或回调继续访问已释放对象，也避免把复用的 fd 误认为原连接。

- 对端关闭导致的发送失败只影响相关连接；处理 SIGPIPE 等进程级副作用，不能让一次异常连接终止服务器。

这些语义分别参照 [recv](https://man7.org/linux/man-pages/man2/recv.2.html)、[send](https://man7.org/linux/man-pages/man2/send.2.html) 和 [epoll_ctl](https://man7.org/linux/man-pages/man2/epoll_ctl.2.html)。读端半关闭后是否排空已生成回复，应在实现时明确并加入测试；不能仅凭 HUP 事件就把尚未读取的数据误认为不存在。

当后续加入命令预算或暂停读取后，已有完整请求可能仍在 incoming。此时需要应用自己安排继续处理，LT 也不会代替应用调度用户态缓冲中的工作。[epoll](https://man7.org/linux/man-pages/man7/epoll.7.html)

## 输出硬上限的精确定义

连接的输出硬上限约束“尚未成功交给内核的应用输出字节”，包括 RESP 编码开销。统计应基于未发送区间，而不是把已发送前缀重复算入。

ReplyWriter 追加将超限时报告失败，连接停止继续执行请求并进入关闭路径。可以在整条回复编码前计算预算，或使用不会超过上限的受检追加；不能截断一条回复后继续维持正常协议会话。

这项保护的边界必须明确：

- 它不限制所有连接加起来的输出，也不限制数据库总量或进程 RSS。容器 capacity、输入缓冲和其他分配仍占内存。

- 它不等于内核发送缓冲的上限。send 成功也不表示客户端应用已经读取回复。

- 客户端停止读取后，内核可能暂时吸收输出，随后非阻塞发送才遇到 EAGAIN，应用输出开始积压。

- 超限断连可能丢失尚未交付的回复。此前已经成功执行的 SET 或 DEL 不因此回滚，客户端可能无法仅凭断连判断命令是否执行。

- 即使客户端正常读取，如果服务器先集中生成整个批次的回复再发送，也可能撞到硬上限。测试需要区分服务端批次积压与真正的慢客户端。

内核发送行为参照 [send](https://man7.org/linux/man-pages/man2/send.2.html)。Redis 文档也区分输出硬上限与按持续时间判断的软上限；本项目未来候选的“高低水位暂停和恢复”不等同于 Redis 的软上限断连机制。[Redis 客户端处理](https://redis.io/docs/latest/develop/reference/clients/)

## 存储层演进边界

首版键索引使用 std::unordered_map。命令层通过 Database 的操作接口访问，不暴露容器或条目来进行任意修改。当前存储值在语义上只有字符串；是否增加 Value 包装、Entry 字段及具体返回类型，是局部实现选择。

| 后续工作 | 主要发生变化的模块 | 首版应保留的边界 |
| --- | --- | --- |
| 自写哈希表及渐进迁移 | Database 内部键索引与数据结构实现 | 命令层继续调用数据操作；不依赖桶或迭代器 |
| ZSet | 数据对象、类型操作、对应命令和必要的回复编码能力 | 类型检查集中在存储操作中；协议解析继续提供参数范围 |
| 定时器与 TTL | 定时调度、过期索引、Database 查找和删除路径 | 查找、删除和条目生命周期有统一入口；事件等待超时可接入下一期限 |
| 大对象后台销毁 | 对象脱离索引、所有权交接、后台任务队列 | 活跃数据库继续由主线程管理；待销毁对象须已无其他使用者 |
| 分段缓冲或池化 | Buffer、Range、网络 I/O 适配 | 上层借用范围与同步有效期不绑定某个连续容器 |
| 命令预算或高低水位 | 调度、连接状态、继续执行机制 | 保留“处理一条完整请求”的步骤，解析与命令代码可复用 |

演进目标是把修改集中到相关模块。新增类型和生命周期规则仍可能扩充接口；不承诺以后所有接口完全不变。教程相关实现见 [哈希表](https://build-your-own.org/redis/08b_hashtables_impl)、[ZSet](https://build-your-own.org/redis/11_sortedset)、[TTL](https://build-your-own.org/redis/13_heap)、[线程池](https://build-your-own.org/redis/14_thread)。

## 首版验收与可复现基线

| 验收组 | 必须覆盖的用例 |
| --- | --- |
| 命令语义 | PING 两种形式；SET 新建与覆盖；GET 命中、不存在和空字符串；DEL 多 key、重复 key 与不存在 key |
| 错误语义 | 未知命令、参数数量错误、不支持的 SET 选项；确认错误命令没有修改数据库，后续合法命令仍能执行 |
| 协议边界 | 每个可能的切分位置、CRLF 跨读取边界、payload 中含零字节或 CRLF、多请求合并到达、大请求跨多轮事件循环 |
| 读写与连接 | 部分发送、EAGAIN、对端断开、半关闭策略、fd 复用；确认字节不重复、不丢失、不乱序，连接资源能释放 |
| 输出保护 | 只发请求不读回复、限速读取、回复放大；触及硬上限时正确断连，其他连接继续服务 |
| 输入保护 | 超长数字、长度溢出、过多参数、超限请求、截断输入；在越界或危险分配之前处理 |
| 空闲行为 | 无待发数据的连接不会因永久关注 EPOLLOUT 而持续空转 |
| 性能基线 | 固定版本与构建模式，记录 SET/GET 的吞吐、延迟分布、CPU、内存及错误和断连情况；保存原始结果 |

首版验收重视能暴露真实错误的边界测试。诊断时可使用 sanitizers、strace、分配统计和 profiler；正式性能对照保持观测方式一致，避免将诊断开销混入版本比较。压测工具的测试项选择参照 [redis-benchmark 文档](https://redis.io/docs/latest/operate/oss_and_stack/management/optimization/benchmarks/)。

## 实现时固定的配置与局部选择

以下项目集中设置、写入配置说明和实验记录即可，不需要再拆成多轮架构问答。

| 项目 | 实现时应记录的内容 |
| --- | --- |
| 请求限制 | 单个 bulk、单条请求、参数数量、长度字段的限制及超限行为 |
| 缓冲限制 | 输入保留上限、输出待发送硬上限、初始容量、扩容和整理条件、容量回收方式 |
| 调度批次 | 单次有限读取批次、事件数组规模、接受连接与发送批量；它们不等于已选择命令轮转预算 |
| 连接与服务配置 | 监听地址和端口、连接上限、fd 限制处理、半关闭及退出清理策略 |
| 构建与测试 | C++ 标准、编译器与优化级别、构建工具、测试工具、客户端版本 |
| 内部表示 | 游标坐标、具体连续容器、命令分发形式、Value 或 Entry 是否包装、错误返回方式 |

限额之间需要一致：例如允许保存的最大字符串，应能在空输出缓冲时生成合法 GET 回复；若要允许更大的单条回复，就需要明确另一种发送策略。不要把演示用数字或 Redis 默认值自动写成 Redlet 的固定要求。

实现第一版时应保留一个可复现的基准提交或标签。后续优化参考表中的每项实验，再记录对应的基线提交、优化提交、配置、负载与原始数据。
