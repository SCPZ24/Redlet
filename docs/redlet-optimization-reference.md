# Redlet 后续优化参考表

基准日期：2026 年 11 月 3 日。对应 Redlet 首版：epoll LT、单主线程、连续输入输出缓冲与游标、借用请求范围、ReplyWriter 直接编码、std::unordered_map、输出硬上限断连，以及有限输入批次内处理完完整请求的调度方式。

本表把生产场景转成可验证的实验假设。使用时先构造场景、观察现有行为并定位成本，再决定是否实现候选方案。表中的“当前问题”包含现有保护的边界及条件性风险，不能直接当作已测得的缺陷。

后续工作分为**条件优化**与**后续能力**。条件优化依据首版压测选择，后续能力需要先实现相应章节的数据类型、TTL 或任务机制。并行命令执行属于更大的架构扩展，单独标明，不是当前路线承诺。

## 场景与优化参考表

| 哪种生产场景 | 当前实现在该场景有什么问题 | 如何构造测试用例暴露问题 | 后续优化建议 |
| --- | --- | --- | --- |
| **条件优化 C01** 单个连接的深 pipeline 拖延其他连接 | 当前会处理完一个有限输入批次内的所有完整请求。它会让出主循环，但批次耗时仍可能较长；没有严格的单连接时间上限 | 一个连接连续发送深 pipeline，另一组连接按稳定节奏发送 PING 或小 GET。逐步增加深度；确保请求批次实际足够大且未先触及输出硬上限。单独统计轻量连接 p50/p95/p99、最长等待和单连接处理耗时，同时记录总吞吐 | 若旁路延迟确实恶化，加入每连接命令预算及应用级继续执行队列，轮流推进。完整请求留在 incoming 时必须主动接续；有本地待处理工作时仍定期收集新 I/O。命令数量预算不能抢占单条昂贵命令 |
| **条件优化 C02** 客户端只发请求不收回复，或读取速度低于生成速度 | 非阻塞发送遇到内核容量不足时保留 outgoing。首版在追加回复将使待发送输出超过硬上限时断连，保护单连接积压，但牺牲慢连接的持续服务；内核输出不受同一个计数器直接约束 | 预存合法的大 value；异常客户端循环 GET，却完全不 read，另一轮限速 read。保持健康客户端并行。记录输出生成/发送时机、EAGAIN、应用待发送字节、容量、内核 Send-Q/内存、触顶断连、健康客户端 p99 和成功回复数 | 若需要保留慢连接，加入高低水位：达到高水位时暂停网络读取和已有请求的继续执行，回落后主动恢复。保留硬上限；必要时配合总输出预算。单纯调大缓冲或加池不能解决长期输入输出速率失衡 |
| **条件优化 C03** 大量连接同时有中等输出积压 | 单连接硬上限不能限制所有连接输出之和；每个连接都未触顶时，进程和内核仍可能承受很大总内存压力 | 逐步增加限速读取连接数量，使单个连接稳定在硬上限以下；并行发送健康请求。记录连接数、所有 pending 输出之和、容器容量之和、RSS、socket 内存、错误/断连及正常请求延迟 | 根据总量压力加入全局缓冲预算、连接准入和明确的拒绝策略。将缓冲容量与逻辑待发送字节分别观测。提高单连接上限只改变资源取舍，不自动构成性能改善 |
| **条件优化 C04** 短连接频繁创建与关闭，或长连接数量很多 | epoll 已避免采用 poll 的每轮全量数组方案，但连接建立、关闭、fd 和连接对象管理仍有成本 | 对比相同业务量下的持久连接复用与逐请求重连，分别控制当前连接数和每秒新建连接数。记录 accept/close 次数、CPU、FD、失败率和延迟；检查压测端端口、连接队列及资源是否先成为瓶颈 | 优先让客户端复用连接；若服务端分配确实占主导，再考虑连接对象复用、按需分配缓冲或连接准入。epoll 后端已经确定，不因此要求补做 poll |
| **条件优化 C05** 空闲连接或请求长期只到达一部分 | 非阻塞 I/O 不会自动回收连接。即使长度合法并处于输入上限内，长期半包仍可能占据 fd 与缓冲；首版未承诺空闲或请求完成超时 | 分别建立大量完全空闲连接、发送合法请求前缀后暂停、按极低速补充字节，同时保持正常请求。记录 FD、残留输入、RSS、正常连接建立成功率和资源回收时间 | 后续接入定时机制后，分别设计连接空闲超时与请求未完成超时。检查“偶尔发一个字节”是否会无限延长请求寿命。长度上限和整数溢出检查仍属于首版正确性要求 |
| **条件优化 C06** 大消息、部分发送或流水线流量引起缓冲搬移 | 连续缓冲＋游标已经避免每次消费或发送都删除前缀；仍可能在整理或扩容时复制未消费数据。成本是否显著取决于实际策略 | 输入侧测试大请求分段到达，或先发送半条请求，再追加该请求剩余字节及后续多条完整请求；输出侧测试大回复与受控的部分写入。分别计数整理次数、搬移字节、扩容次数和分配次数，结合 CPU profile 与有效吞吐 | 先调整整理阈值、扩容方式及追加路径；只有搬移成本显著时再评估分段缓冲或适合该场景的环形缓冲。新实现需覆盖头部、长度字段、payload 跨边界的情况 |
| **条件优化 C07** 偶发大流量后，连接长期保留很大的缓冲容量 | 连续缓冲逻辑长度回落，不代表 capacity 或进程 RSS 立即回落。是否长期保留峰值容量取决于尚未确定的回收策略 | 对一组连接制造大流量突发，然后恢复长期小请求；与从未经历突发的连接对照。分开记录逻辑长度、capacity、总分配和 RSS，观察冷却阶段 | 评估按空闲期或容量比例回收，采用滞后阈值减少反复缩容扩容。分别验证内存减少与下一次突发的分配/延迟代价 |
| **条件优化 C08** 频繁分配释放成为热点 | 借用参数和直接编码已减少部分中间表示，但缓冲增长、参数描述、数据库节点或未来分段块仍可能产生分配开销；首版没有池化承诺 | 分别测试连接 churn、小消息高频处理和大小交替的突发，记录分配调用、分配字节、CPU 占比、峰值与空闲后内存。先定位具体分配来源 | 先复用已有容量或元数据空间；若以后采用分段缓冲且块分配成本突出，再考虑块池。池需有回收和总量边界，不能把更多常驻内存误算为免费加速 |
| **条件优化 C09** 合法请求被切成很多小片段 | 首版保证半包正确性，但未确定解析器保存多少扫描状态。如果实现每次从头扫描，碎片输入可能放大重复解析成本；这是条件风险 | 同一合法请求分别完整发送和按小片段发送，包含长度字段跨片段、较多参数和较长 payload。统计解析耗时及扫描/检查字节数，区分额外系统调用成本与重复扫描成本 | 若证据指向重复工作，保存解析状态、当前参数和位置偏移，复用参数描述空间。payload 已有长度时避免无意义扫描；始终维护追加后的游标有效性 |
| **条件优化 C10** 长 key 查询中的临时字符串复制占比明显 | 参数已借用输入范围，但 Database 的具体查找实现仍可能构造临时拥有型 key；借用接口并不证明整条路径无复制 | 固定命中率及很小的 value，逐步增加 key 长度，分别测命中和未命中的 GET。记录每请求临时分配、复制字节、哈希及比较成本；避免让大回复掩盖 key 查找成本 | 按证据使用支持借用范围的查找、透明哈希/比较或局部适配。存储 key 与查询范围必须使用一致的哈希和相等语义；SET 入库仍需取得数据所有权 |
| **条件优化 C11** 键空间持续增长，在哈希表扩容时出现延迟尖峰 | std::unordered_map 在增长过程中可能发生较长的 rehash；当前主线程会被这次操作占用。只测预热完成后的 GET 会漏掉此场景 | 先预存一组常读 key，再持续 SET 新 key 扩大键空间；旁路对预存 key 做稳定 GET。记录 bucket 数变化、插入时点、扩容附近的延迟、最大事件处理时间和峰值内存；另测只覆盖已有 key 的对照 | 容量可预估时先比较 reserve。后续自写哈希表可评估渐进 rehash。要归因于迁移策略，在同一实现中控制哈希函数、负载因子和节点布局，对比集中迁移与分批迁移 |
| **条件优化 C12** 一条合法命令本身耗时很长 | 首版同步执行整条命令，无法在命令内部抢占；即使以后加入命令数量预算，也只能在命令之间让出。大 GET 的复制编码、多 key DEL 或一次扩容，都可能使主线程较久不能处理其他连接 | 在允许的尺寸和参数上限内，分别增加 GET value 大小与 DEL 参数数量；旁路发轻量请求。记录单命令执行/编码时间及旁路延迟，区分网络等待与 CPU 工作 | 先减少热点复制或数据操作成本，并合理配置单命令工作量。若考虑分片执行，必须同时明确原子性与一致性；不能在未评估语义的情况下把半条命令交错执行 |
| **后续能力 F01** 大 ZSet 等对象删除或覆盖时集中析构 | 需要先实现复杂数据类型。主线程同步释放很多成员时可能暂停服务；首版字符串释放不能直接代表该成本 | 在支持相应类型后构造不同成员规模的对象，执行删除或确实会销毁旧值的替换，同时旁路发 GET/PING。记录销毁时间及旁路尾延迟；优化后增加任务队列与待释放字节观测 | 将已从键索引、TTL 等结构移除且无人使用的对象，转交后台独占销毁。活跃数据库继续由主线程管理；限定队列积压并观察实际释放进度，不能把释放延后当作内存已回收 |
| **后续能力 F02** 大量 key 在同一时刻过期 | 首版没有 TTL；后续若一次清理所有到期项，查找、删除和析构可能形成集中工作 | TTL 实现后，对比相同数量 key 的分散到期和集中到期；同时查询未过期 key。分别覆盖大量小对象与少量大对象，记录清理耗时、旁路 p99、过期积压与实际回收延迟 | 评估每轮过期清理预算、下一期限调度、查询时的过期判断以及必要的后台释放。一起衡量请求延迟和过期积压，不能仅因少清理而延迟下降就判为成功 |
| **较大架构扩展 X01** 单个 CPU 核心持续饱和，业务需要更高整体吞吐 | 网络、命令和活跃数据在一个主线程中，无法并行使用多个核心执行普通命令。增加连接数与增加 CPU 执行并行度不是同一件事 | 先排除压测端、网络、容器 CPU 配额和单个慢操作，确认服务端热点与单核饱和。改变连接数、pipeline 和请求分布，记录每核 CPU、吞吐平台及尾延迟 | 需求明确后再比较进程/数据分片、多个事件循环或其他所有权划分。跨线程队列、请求顺序和共享数据同步需要重新设计；一个全局数据库锁不会自动带来并行收益 |

## 实验必须保留的首版正确性

半包与多请求处理、二进制安全、非法长度和整数溢出检查、部分发送、EAGAIN、连接清理、借用范围有效期及同连接顺序，都属于首版验收。它们不能以“以后优化”为由省略。

基线已经使用游标，因此不能把“每次发送都 erase 前缀导致反复搬移”写成首版的既有问题。基线已经借用参数并使用 ReplyWriter，因此不能虚构一个复制完整请求或完整 Reply 树的当前实现来制造优化百分比。未选定的内部实现，只能通过检查代码与测量确认。

命令或资源限额相同的对照中，成功回复、错误、拒绝、超时和断连分别计数。提前丢弃连接、少处理请求或减少协议检查带来的数字变化，不能当作等价服务下的性能提高。

## 四组优先可执行的测试方案

### 深 pipeline 与轻量请求混合

先运行只有轻量客户端的基线，再加入一个高负载连接。轻量组保持相同 key、value、发送节奏和连接数，高负载组逐级增加 pipeline 深度。使用足够轻的命令与回复，尽量让输出硬上限不先成为决定因素。

为两组分别计时和统计错误。记录轻量请求从计划发送到完成的时间，以及压测端实际延迟发送的情况，避免把压测客户端自身排队隐藏掉。服务器记录每次处理某连接的完整命令数和耗时，确认确实形成了较长批次。

延迟上升不自动证明单连接批次不公平，因为加入高负载连接也增加了总负载。结合主循环处理耗时，确认延迟是否与长批次相关；必要时增加相同总请求率、但分散到更多连接或较浅 pipeline 的对照，以区分批次独占与总体过载。

若轻量组延迟没有稳定恶化，或负载被固定输入批次自然分散，这也是有效结论。加入预算后的实验还要检查：incoming 留有完整请求、内核暂时无新数据时，连接仍能继续推进；同时没有重复入队、忙循环和回复乱序。

### 只发不收与限速读取

先通过健康连接写入一个合法的大 value。其单条 GET 回复在空 outgoing 中应小于硬上限，避免把“单条回复不被允许”混入慢读取测试。

异常客户端持续发送短 GET 请求，第一组完全不读取回复，第二组以受控速度读取；生产端自身也使用可观察的非阻塞发送或受控批次，记录它是否因服务器停止读取而受阻。独立健康连接持续做小请求。

测试应持续到出现明确的发送受阻或触顶事件。少量请求可能全部被内核暂时接收，尚未暴露应用积压。观测至少包括：

- outgoing 未发送字节与 capacity，以及它们的增长时间线。

- send 的正数返回、部分发送、EAGAIN 和触顶断连时点。

- 服务器 socket 的发送队列和内核内存，可借助 ss -tinm 观察；进程 RSS 单独记录。

- 健康连接的成功回复和尾延迟。

如果尚未出现发送受阻，就因“先执行整个批次、后发送”触及上限，先记录服务端生成与 flush 的顺序。该结果不能直接证明客户端读取能力不足。高低水位实验还要验证恢复时主动执行已有完整请求，并恢复相应的 I/O 关注。

内核在非阻塞发送无法继续时返回 EAGAIN，且 send 成功不保证对端应用已经读取。[send](https://man7.org/linux/man-pages/man2/send.2.html) ss 可分别显示 socket 队列与内核内存信息。[ss](https://man7.org/linux/man-pages/man8/ss.8.html)

### 连续缓冲搬移与容量保留

输入和输出分别测试、分别计数。第一阶段是稳定小消息；第二阶段引入合法大请求或大回复，并制造分段接收或部分发送；第三阶段回落到小流量，保持连接存活。

除了吞吐与延迟，直接计数整理时搬移的字节、扩容次数、分配次数和实际容量。若大部分 CPU 不在搬移与分配，分段或池化就缺少直接依据。若 capacity 回落而 RSS 未立即回落，还要区分容器释放、分配器保留和操作系统内存统计。

分段缓冲改变物理布局；块池改变申请与回收方式。先分别验证收益，再考虑组合。若合并修改，只能先报告整体方案差异，不能自动把收益全部归因于其中一项。

### 增长阶段与哈希表迁移

保留三种独立负载：只读已存在 key、覆盖已有 key、插入新 key 扩大键空间。第三组之外，再运行固定节奏的旁路 GET，以观察插入停顿对其他请求的影响。

在调试或诊断构建中记录扩容发生时点和 bucket 数变化；正式对照使用相同观测配置。除了全程 p99，还要观察扩容附近的窗口和最大延迟，因为稀有停顿可能被全程分位数掩盖。

标准库哈希表与自写哈希表比较的是整体实现。若要研究渐进迁移本身，使用同一自写实现的集中迁移与分批迁移模式，并记录负载因子、哈希函数、节点布局、分配方式和内存峰值。迁移分批不意味着所有分配、扫描或释放都有严格的时间上限。

标准库 rehash 的复杂度和接口见 [C++ 无序关联容器要求](https://eel.is/c++draft/unord.req)。教程的新旧表及逐步迁移实现见 [哈希表第二部分](https://build-your-own.org/redis/08b_hashtables_impl)。

## LT 模式下的优化边界

网络层仅使用 Linux epoll 默认的 LT（水平触发）。性能优化围绕读写批次、事件关注与应用调度展开，记录 epoll_wait 调用次数、返回事件数及读写系统调用次数，结合吞吐、尾延迟与 CPU 判断收益。

优化后仍需覆盖部分读取、部分发送、写缓冲从空变为非空、暂停与恢复、半包、深 pipeline 和连接关闭。outgoing 清空后撤销 EPOLLOUT 关注，已有完整请求留在用户态缓冲时由应用主动安排继续处理。

| 版本 | 基线提交、优化提交、是否有额外功能或语义变化 |
| 构建 | 编译器、C++ 标准、优化级别、调试或 sanitizer 状态 |
| 环境 | CPU、内存、内核、容器资源配额、客户端和服务端是否共机 |
| 客户端 | 工具版本、完整参数或脚本、发送节奏、客户端是否先饱和 |
| 工作负载 | 连接数、活跃比例、pipeline 深度、读写比例、key/value 长度分布、命中率、数据集规模 |
| 服务配置 | 请求与输出限额、读取批次、发送策略、容器预留容量及相关 socket 设置 |
| 有效服务量 | 成功回复数与每秒成功请求数；错误、拒绝、超时和断连单独统计 |
| 延迟 | 分组 p50/p95/p99，必要时 p99.9、最大值和事件窗口；不能把多个客户端的 p99 直接取平均当作总体 p99 |
| 资源 | CPU、内存、缓冲逻辑长度与容量、fd、系统调用、分配和复制计数；按当前假设选择必要指标 |
| 阶段 | 预热、稳定状态、增长/突发、冷却回收分别观察；重复运行并报告波动 |
| 结论 | 是否复现问题，优化了什么，代价是什么，适用场景及保留或撤回决定 |

性能诊断与正式对照分开。strace、分配追踪和 profiler 帮助找热点，但其开销可能改变数字；两组正式测量应使用一致的观测配置。工具支持的测试项和 pipeline 参数可参照 [redis-benchmark](https://redis.io/docs/latest/operate/oss_and_stack/management/optimization/benchmarks/)。

简历表述应在实验结束后填写，例如：“采用【技术】，在【连接数、请求分布、数据规模】场景下，使【指标】由【基线值】变为【优化值】，同时【资源代价或适用限制】。”吞吐提升比例使用“优化值 / 基线值 − 1”；延迟下降比例使用“1 − 优化值 / 基线值”。没有稳定收益也是可接受的工程结论。

## 后续能力的资料依据

后台销毁场景对应教程 [线程池](https://build-your-own.org/redis/14_thread)：主线程先完成逻辑删除，再将合适的大对象销毁任务交给后台。具体节点阈值、线程数和任务队列限制需要自己的测量，不能直接把教程数字当作项目承诺。

集中到期场景对应教程 [TTL](https://build-your-own.org/redis/13_heap)：每轮清理量与下次事件等待共同影响请求延迟和过期积压。首先保证逻辑过期语义，再衡量实际回收的滞后。

Redis 的输出硬上限、按持续时间判断的软上限及客户端资源管理可参照 [客户端处理文档](https://redis.io/docs/latest/develop/reference/clients/)。本项目候选的高低水位暂停/恢复属于背压策略，不能与 Redis 的“软上限后断连”混用名称。
