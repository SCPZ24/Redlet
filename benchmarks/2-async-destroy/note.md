# 异步回收对事件循环延迟的削峰实验

## 目标

对比 `./redlet-expire` 和 `./redlet-async-destroy`，观察大 SortedSet 集中释放时，事件循环响应延迟的峰值能降低多少。

同步版在事件循环中逐个释放成员，异步版将释放任务交给工作线程。使用持续 PING 的 RTT 作为事件循环响应能力的外部观测指标，其中也包含本机网络和客户端调度开销。

## 实验设计

每轮预装 8 个 SortedSet，每个 100,000 个成员。在持续 PING 期间，一条 DEL 删除全部集合。

```mermaid
flowchart LR
    A[启动空实例] --> B[预装并校验数据]
    B --> C[PING 预热 2 秒]
    C --> D[记录正常延迟 2 秒]
    D --> E[另一连接集中 DEL]
    E --> F[继续观测 5 秒]
    F --> G[保存延迟样本并结束本轮]
```

- 预装后触发删除，将数据构建与析构的开销分开测量。
- 集中 DEL 提供明确的触发时刻，便于对齐两个版本的延迟曲线。
- 删除前的 PING 窗口提供同一轮的正常延迟参考。
- 每轮使用新实例和相同数据，保证 DEL 实际释放相同数量的成员。

## 环境控制

- 在当前 Redlet Linux 开发容器的 `/workspace` 执行。执行前通过 `docker ps` 和 `docker inspect` 确认容器及挂载。
- 两个版本使用相同的两个服务端 CPU，客户端固定到另一个 CPU。CPU 编号从容器允许列表选择，异步版工作线程数为 1。
- 两个版本顺序运行，共用 `127.0.0.1:6379`。端口已有服务时中止，仅停止本轮启动的进程。
- 每个版本五轮，按轮次交替先后顺序。保持数据、发压速率、CPU 配置和观测时长一致。
- 保存产物 SHA-256、构建参数来源、CPU 配置及容器内存限制。该实验结论对应上述双核服务端预算。

## 数据准备

- 键名为 `bench:z:0` 至 `bench:z:7`。
- 每个成员为固定 32 字节 ASCII 字符串，包含补零后的唯一序号，score 使用该序号。
- 每条 ZADD 写入 256 个成员，共 514 个参数。生成 RESP 数据流，通过 `redis-cli --pipe` 导入。
- 导入错误数必须为零，回复数符合预期。每个集合最后一个成员的 ZRANK 应为 `99999`。
- 执行前确认内存足以容纳数据。若需缩小规模，两个版本统一调整，并记录实际参数。

## 延迟采样

### PING 探针

使用预先建立的独立长连接，每秒计划发送 1,000 个 PING。发送与接收分开处理，按回复顺序匹配请求。

逐请求记录单调时钟时间。

- 计划发送时间。
- 实际发送时间。
- 完整回复到达时间。

RTT 为回复到达减去实际发送。另记录发送调度延迟和计划到回复的延迟，用于识别客户端自身的发压停顿。

持续按计划发送，可以保留服务端阻塞期间的请求需求。逐条等待回复的方式会在阻塞期间降低发压速率，使慢请求比例偏低。

### 删除触发

预热和正常窗口结束后，通过另一条已建立的连接执行一次 DEL，删除全部 8 个 key。记录发送、收到回复的时刻，校验返回值为 `8`。

从 DEL 发送时刻起继续发压至少 5 秒，并覆盖 DEL 回复后至少 1 秒。随后停止发送，收齐已发送请求的回复，设置接收超时。记录实际观测长度。

校验 key 已删除放在采样结束后。回复错误、超时、连接断开或进程退出均将该轮标记为失败，并保留日志。

## 关键数据

| 指标 | 用途 |
| --- | --- |
| PING 最大 RTT | 主要削峰指标 |
| PING p99、p99.9 | 比较两个版本中较慢请求的延迟水平 |
| DEL 响应耗时 | 辅助解释同步释放造成的阻塞 |
| 发送调度延迟 | 判断客户端是否干扰测量 |

分别统计删除前 2 秒、DEL 发送后固定 5 秒的样本。按请求实际发送时间归属窗口，窗口内发出的请求即使稍后完成也纳入统计。保留全部样本，展示以 DEL 发送时刻为零点的延迟曲线。

将 RTT 从小到大排序，p99 和 p99.9 分别取第 99% 和第 99.9% 位置的延迟值。它们由实测样本计算，直接用于版本对比。

单次删除产生的慢请求可能被 p99 稀释，因此优先比较最大 RTT，并结合延迟曲线观察尖峰的高度和持续范围。

五轮逐轮展示，再汇总各轮最大 RTT 的中位数及最差轮次。削峰比例为 `(基线峰值 - 新版峰值) / 基线峰值`，分别对中位数和最差轮次计算。
