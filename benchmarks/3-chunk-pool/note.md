# Redlet 输出缓冲区优化：背景与对照实验

> B0/O 的 No-delay off/on 完整实验均已完成，结果与复现方式见第 9、10 节。
> 整理日期：2026-11-09。  
> 实现契约见同目录 [plan.md](./plan.md)。  
> 本轮要回答：相对于提高发送预算后的基线，页式输出队列和可回收内存池能否减少搬移与长期闲置内存，同时不以明显的尾延迟恶化为代价？

## 1. 问题背景与目标场景

Redlet 已完成教程基线。本轮希望通过自主设计解决输出路径的具体问题，而不是把协议开关或发送预算调整包装成内存池成果。

### 1.1 当前输出路

B0 的 Connection 用 `std::string outcoming` 持有回复，部分发送后，下次发送前执行 `erase(0, delivered_pos)`；ReplyWriter直接向该字符串编码。`OUTPUT_BUFFER_SIZE` 为 64kb（原先为1kb，现已修改。以当前64kb的版本为极限。编译产物），`MAX_OUTPUT_BYTES` 为 4 MiB。

这个源码快照不是用户随后本地修改的证明。实际 benchmark 以固定的完整 commit SHA、工作区状态、构建参数与二进制为准。

### 1.2 三类问题

**反复搬移。** 一个积压回复分多次发送时，删除前缀会搬移剩余部分。对于总长 N、每次完整发送 B 的简化情形，搬移量为 `(N-B)+(N-2B)+...`；发送批次越小，放大越严重。提高 B 可以缓解，但不从机制上消除它。

**容量与单连接历史峰值绑定。** 连续缓冲没有明确回收策略时，偶发大回复后可能保留较大的 capacity。长连接保持存活，但其输出已很小；很多连接各自保留一份峰值容量，是这次主要的内存目标。

**扩容与回收的延迟代价。** 连续缓冲增长可能复制已有内容；激进回收又可能增加后续分配。分块、共享池和页级回收也有遍历、系统调用、元数据和重新触页成本，不能预先保证所有负载都更快。

### 1.3 选定的业务形态

大量长连接多数时间返回小回复，偶尔读取 64 KiB～1 MiB 的文本/JSON/文档；部分连接会 pipeline 批量读取，另有少数慢客户端造成输出积压。

重点不是“所有连接一直各压着 1 MiB”，而是 **响应大小波动、活跃连接轮换、已发送数据不应长时间占用连接私有容量**。真正尚未发送的有效数据不能凭空省掉。

## 2. 优化方式与预期边界

方案采用页大小 Chunk、两游标队列、跨连接共享池、`sendmsg` 聚集发送。空页先保留供快速复用，超出阈值且空闲足够久后 `MADV_DONTNEED`；整个 Slab 完全空闲再解除映射。详细状态机和接口见 [plan.md](./plan.md)。

这里借鉴的是“按块管理与复用”的思想，不实现 vLLM 的 KV cache、逻辑块表或注意力访问机制，也不把通用内存池技术声称为首创。

| 预期收益 | 必须承认的成本或限制 |
|---|---|
| 不因消费前缀而搬移剩余回复 | 仍需把回复数据复制到输出页，并经过普通 socket 发送 |
| 扩大输出队列只追加页，不重分配已写内容 | 页链接遍历、iovec 组织和控制块增加成本 |
| 页可跨连接复用，连接发空立即归还 | 同时在途的小回复每个仍可能占一页 |
| 局部空闲 Slab 内也能回收空闲页 | 活页仍会保留 Slab 的地址映射与部分元数据 |
| 空闲 RSS 可以下降 | 回收后的首次写入可能增加缺页处理与尾延迟 |

不能把“归还 free list”当成“操作系统已经收回内存”。`MADV_DONTNEED` 保留映射而改变私有匿名页的内容语义；`munmap` 才解除映射。[madvise][madvise]、[mmap][mmap]

## 3. 固定基线与比较版本

### 3.1 基线准备

用户先把单次发送预算提高，建议先用 64 KiB：

```cpp
inline constexpr int OUTPUT_BUFFER_SIZE = 64 * 1024;
```

不要改 `MAX_OUTPUT_BYTES` 或输入读取量来放大收益。若用户选了其他预算，以实际值为准，并在所有结构对照中统一。

当前项目目录中，redlet-64kb-buffer是一个优化前的，`OUTPUT_BUFFER_SIZE = 64 * 1024`的已经编译好的版本。

### 3.2 比较版本

| 标识 | 内容 | 要回答的问题 |
|---|---|---|
| B0 | 提高发送预算后的原始 `string + erase` | 对用户基线的整体改善是多少？ |
| O | 页式 OutputBuffer + ChunkPool + 聚集发送 + 页/Slab 回收 | 内存和尾延迟的最终取舍如何？ |

**发送预算的提升发生在 B0 之前，不计入内存池收益。**

## 4. 实验前的固定条件

### 4.1 环境

正式跑实验前收集：

```bash
git rev-parse HEAD
git status --short
uname -a
getconf PAGESIZE
getconf IOV_MAX
getconf GNU_LIBC_VERSION
c++ --version
ulimit -n
cat /sys/kernel/mm/transparent_hugepage/enabled
```

记录 CPU 型号、可用核数、内存/cgroup 限额、swap、编译器完整参数、标准库/allocator、内核、Docker 与宿主环境、Transparent Huge Pages 状态。无法读取的项目标记 unavailable，不猜测。

容器仍共享宿主 CPU、网络等资源。记录干扰，不把容器结果当成独占物理机极限。

### 4.2 所有版本保持一致

- 编译优化、断言/sanitizer 状态、命令实现、数据集、worker 数。
- 发送字节预算、输入预算、每连接输出上限、TCP 配置、socket buffer 配置。
- 连接数、pipeline 深度、请求序列、随机种子、客户端读取速度。
- 服务端与压测客户端尽可能绑定不同 CPU；已有后台线程数保持一致。
- 性能运行不带 ASan/UBSan；正确性和详细跟踪另跑。

回收定时器新增的空闲唤醒和维护时间是 O 的真实成本，应报告，不从统计中删掉。

### 4.3 数据集与负载发生器

先预装共享的 64 B、64 KiB、1 MiB value，每种少量固定 key 即可。多个客户端读取同一批预装数据，避免为每连接单独创建大 value，把数据库内存误算为输出缓冲。

结果表中的负载参数采用以下含义。

| 参数 | 含义 |
|---|---|
| 64 B、64 KiB、1 MiB | 每次 GET 读取的 value 大小，实际回复还包含 RESP 协议头和结尾 |
| C | 客户端连接数 |
| P | 每条连接的 pipeline 深度，即等待回复前连续发送的请求数 |
| QPS | 每秒完成的单条 GET 数量 |
| RSS | 服务端整个进程当前驻留在物理内存中的大小，包含数据库、输出缓冲区、池内驻留页面和其他运行时内存 |

例如 `64 B，C8/P32` 表示 8 条连接各自按批发送 32 个 GET，每个 GET 读取 64 字节的 value，最多有 256 个已发送但尚未收齐回复的请求。本次客户端在每条连接上收齐当前批次的全部回复后，再发送下一批。P=1 的延迟覆盖一条完整回复，P>1 的延迟覆盖一整个批次，B0/O 延迟对比保持相同的 C 和 P。服务端仍按事件循环处理命令，pipeline 允许客户端同时保有多个在途请求。

预装完成后等待已有后台任务结束，再建立正式连接并开始记录。正确解析每条 RESP 回复，至少在验证运行中逐字节核对；正式负载的校验方式和客户端 CPU 消耗记录清楚。不要先压测再把慢客户端丢掉的请求当成功。

## 5. 测量指标与口径

### 5.1 内存指标

| 指标 | 含义 | 采集方式 |
|---|---|---|
| 当前 RSS 时间序列 | 进程当前驻留内存 | `/proc/PID/smaps_rollup` 的 `Rss`，无权限时注明降级 |
| 峰值 RSS | 一轮运行最大驻留量 | 采样峰值，并辅以新进程的 `VmHWM`/`ru_maxrss` |
| 空闲阶段 RSS | 大响应完成但连接仍存活的占用 | 排空后固定时间点采样 |
| VmSize | 虚拟地址范围规模 | `/proc/PID/status` |
| VmPTE | 页表内存 | `/proc/PID/status`，不假定页级丢弃立即消除页表 |
| 池 mapped / InUse / Warm / Cold | 实现内部逻辑账目 | 低频快照 |
| pending bytes / connection capacities | 真正未发送数据与基线保留容量 | 测试计数器 |
| 元数据字节 | 控制块/Slab 估算占用 | 数量 × 实际 sizeof，注明 allocator 开销未完全覆盖 |
| 缺页计数 | 回收后复用成本 | `ru_minflt/ru_majflt` 或 `/proc/PID/stat` 阶段差值 |

`smaps_rollup` 汇总映射驻留信息；`status` 的快速 RSS 统计可能不够精确。`VmHWM` 和 `ru_maxrss` 是历史峰值，**不能用来证明内存回落**。[Linux /proc][proc]、[getrusage][getrusage]

进程 RSS 不等于“程序相关的全部系统内存”。输出已经进入内核 socket 缓冲后，应用页可以归还，但网络仍可能占用内核内存。比较版本统一 socket 参数，并在背压实验中补充 socket/cgroup 指标，说明统计范围。

建议每 100～250 ms 采样一次内存；对短突发补充阶段屏障和内部峰值计数。采样本身有成本，p99 主结果另跑低扰动轮次，不把高频扫描 `/proc` 当作免费。

### 5.2 延迟与吞吐

| 指标 | 口径 |
|---|---|
| P1 请求延迟 | 从计划/实际提交点到完整收到对应 RESP 回复；明确使用哪个起点 |
| Pipeline 批次延迟 | 一批提交到该批完整收齐，不能标成单请求延迟 |
| 小请求 p50/p95/p99 | 小请求单独统计，不与大请求混合一个直方图 |
| 大请求/冷启动 p99 | 稳态与回收后的重新触页阶段分开 |
| 有效吞吐 | 成功、完整且正确的请求数/秒；失败和断连另列 |
| 回复字节吞吐 | 实际收到的协议字节/秒，另报 payload 大小 |
| 服务端 CPU | 用户态/内核态时间及占用 |
| 维护耗时 | maintain 的调用数、分位数、最大值与预算耗尽次数 |

吞吐测试可以用 closed-loop 饱和负载。混合负载的公平性/尾延迟实验另用统一固定到达率，选择低于各版本可持续吞吐的相同压力，避免各自满负载造成不可比。

固定到达率测试需记录计划发送时间、实际发送时间、完成时间；发生排队或负载发生器跟不上时不能悄悄降低请求率，否则可能漏掉拥塞等待。负载发生器先饱和的结果不能解释成服务端上限。

## 6. 工作负载矩阵

以下数值是可复现的起始参数。资源不足时降低规模，但同一比较组必须统一，不为某个版本单独改小。

| 场景 | 初始配置 | 核心观察 |
|---|---|---|
| S1 小回复常态 | 64 B GET，C=1/64/256，P=1；另测 C=8、P=32 | 页粒度和链表管理是否损害小请求 |
| S2 大回复/批量回复 | 1 MiB GET，C=1/8、P=1；64 KiB GET，C=1/8、P=16 | 搬移、CPU、吞吐、大响应延迟 |
| S3 长连接偶发大响应 | 256 长连接，16 个一组轮流各读 1 MiB，全部保持连接 | 跨连接复用与突发后的容量/RSS 回落 |
| S4 慢客户端与正常流混合 | 64 个小请求连接 + 4 个 1 MiB 慢读连接 | 小请求 p99、在用内存与回收干扰 |
| S5 每 Slab 留一个活页 | Pool 独立机制测试，32 或 64 Slab | 活页是否阻止其他页的物理回收 |
| S6 回收后再次突发 | S3 周期重复，短/长间隔分组 | Warm 复用与 Cold 缺页的延迟取舍 |
| S7 超限/故障 | 降低池上限，注入映射/回收失败 | 正确失败、无泄漏，不作为吞吐收益样本 |

C 为总连接数，P 为每连接每批请求数。注意协议 framing 也占输出上限：64 KiB×16 加 framing 约 1 MiB，处于 4 MiB 限额以内。

### S1：小回复不能只测空闲连接

分别测大量空闲长连接与真正同时有小回复的连接。O 的空闲连接不借页，但每个仍有未发送数据的连接至少借一页；这两种状态不能混用来宣传内存优势。

测稳定请求、低频请求和小 pipeline。记录峰值在用页数、RSS、有效 QPS、CPU 和小请求 p99。没有改善或略有回退也如实保留。

### S2：已提高发送预算后的大回复

先跑 B0，再交错跑O。统计输出搬移字节、payload 复制字节、发送调用数、iovec 数、CPU 和完整回复延迟。

O 消除了输出前缀搬移，但不保证消除所有复制。以实际计数解释结果，不能只凭算法名称归因。

### S3：本轮最重要的内存实验

1. 启动新服务端，预装共享数据，等待后台任务稳定。
2. 建立 256 个长连接；用小请求稳定运行 5 秒，记录 `R_before`。
3. 每组 16 个连接各发一次 1 MiB GET；完整读完该组后换下一组，直至每个连接都经历大响应。
4. 所有连接仍保持，不关闭。确认全部大回复收齐、服务端 pending bytes 归零，定义此刻为 `t=0`。
5. 继续观察至少 15 秒，在 t=0、0.5、1、2、5、10、15 秒记录 RSS、capacity、映射和页状态。
6. 一组保持完全空闲；另一组每秒发少量小请求，观察持续活跃但无大积压时是否仍可缩容。

初始最大同时回复量约 16 MiB，避免 O 的 256 MiB 池上限介入；B0 则可能逐连接保留曾经扩大的 capacity。这个测试刻意对应“连接轮换、大小波动”场景，不代表所有负载。

然后把波次并发增加到 64，重复观察峰值。若实际在用数据相同且确实必须保留，不能要求页池无条件降低峰值。

不要在观测期间断开连接、清空数据库或重启进程来制造 RSS 回落；当前空闲连接超时也必须足够长，检查实际存活连接数。

建议报告：

```text
residual_bytes(t) = RSS(t) - R_before
release_fraction(t) = (R_peak - RSS(t)) / (R_peak - R_before)
```

只有分母为正且变化明显超过噪声时才报告比例；比例可能受其他内存变化影响，原始曲线不可省略，也不能强行裁剪成漂亮的 0～100%。

可另定义 `T90` 为释放 90% 突发新增 RSS 且保持稳定的时间。若保留 Warm 缓存或其他开销导致达不到，填“未达到”，不能修改定义。

### S4：慢客户端不是可以回收的垃圾

慢连接先请求 1 MiB，再暂停读取一段时间或以约 1 MiB/s 读取。核对服务端确实出现 pending bytes 与 EAGAIN；仅在客户端 sleep 不一定能制造应用积压，因为内核发送缓冲可能已经接收全部回复。

若必须调小 socket 接收/发送缓冲才能稳定触发，所有版本保持同样设置并记录。每连接积压保持在输出限额以下；过载断连另归 S7。

正常连接使用相同固定到达率读取 64 B value，单独记录其 p99。慢连接的完成时间受读取速度限制，不能要求块池突破客户端速率。比较服务器 CPU、在用内存和正常流延迟，而不是只看慢连接 QPS。

### S5：验证 Slab 部分回收，不只验证空 Slab munmap

这个测试直接驱动 ChunkPool，不经过网络，不代替服务端端到端结果。

1. 借满 32 或 64 个 Slab，并真实写入每一页，避免只建立映射却没有驻留数据。
2. 根据控制块所属 Slab，每个保留一个 InUse 页，写入可校验标记。
3. 其余全部归还。此时每个 Slab 都有活页，禁止整体 munmap。
4. 在 O 中记录回收前后状态；本轮机制探针采用默认 Warm 高低水位 128/64。
5. 在有界维护中推进时间直到符合条件的页已全部处理；采集 mapped bytes、RSS 和驻留快照。
6. 验证保留活页内容不变；再次借出 Cold 并写入，验证地址仍可用、数据正确以及缺页计数变化。
7. 最后归还保留页，推进整体空闲期限，验证多余 Slab 确实解除映射、元数据计数下降。

可用 `mincore` 辅助观察映射页的驻留状态，但它只是瞬时快照，不表示独占物理内存；配合 `smaps` 与控制块账目解释。[mincore][mincore]

避免为检查“页是否清零”提前遍历 Cold 页，从而改变后续首次触页实验。清零正确性测试与延迟测试分开运行。

### S6：下一波负载的账也要算

以相同请求序列重复 S3，分别用 0.5 秒和 5 秒间隔；另用超过 10 秒的间隔观察整体 Slab 解除映射后的重新增长。至少跑 10 轮周期。

分别记录每轮首批请求延迟、稳态延迟、Warm/Cold 命中率、增长次数、minor faults 和维护时间。对比 B0 与 O，同时记录 RSS 收益、缺页及重新映射成本。

### S7：容量上限和错误处理

设定较小池上限，制造合法的分配失败和连接关闭；注入第 k 次 acquire、mmap、madvise、munmap 失败。检查无借页泄漏、未发送数据没有被回收、其他连接继续工作。

这些运行的失败、断连、超时完整计数，不能与无错误的吞吐结果混为一组。正式吞吐实验中，O 不能因为更早拒绝请求而获得“低延迟”。

## 7. 重复、统计与诊断

每个正式版本/负载组合建议至少 5 个独立重复，版本顺序交错或固定种子打乱。稳态测试建议先预热 5 秒，再测 20 秒；突发/冷页测试按阶段执行，不能用预热掩盖待测的首次触页。

每个重复使用新服务端进程，重新准备相同数据。不要把前一个版本的allocator状态、历史峰值或池缓存带到下一个版本。

记录每轮分位数及样本数，报告跨轮中位数和范围。p99 样本不足时明确标注；不要把几轮的 p99 简单平均后称为总体 p99。需要合并时保留兼容直方图或原始延迟样本。

性能运行与以下诊断分离：

- 源码计数：搬移字节、复制字节、分配/借还、维护工作量。
- 系统调用计数：send/sendmsg、mmap、madvise、munmap、epoll；跟踪会扰动时延。
- perf 可用时再采样 CPU 与缺页；权限不足说明限制，不用没有采到的数据推断热点。
- 客户端与服务端 CPU 同时监测；闭环负载的客户端饱和不能归因给服务端。

回环网络结果只说明本机路径；不能用其 GiB/s 数字推断真实网卡带宽或跨机器性能。

## 8. 判定规则

### 必须满足的正确性条件

协议字节完整、连接语义正确、无借页泄漏、限额正确、活数据不回收、失败可控。任何一项不满足都不能以性能收益抵消。

### 要证实的机制

- O 的部分发送不再产生输出前缀搬移，增长不搬移已有 Chunk 数据。
- S5 中所有 Slab 都有活页时，O 仍能回收空闲数据页，而不是只减少内部计数。
- 回收不靠扩大输出限额、丢回复或少做请求换取。
- S6 能量化回收换来的内存收益与下一轮延迟代价。

### 性能目标不预填结论

小请求 p99 或吞吐若在多轮中稳定退化超过约 5%，作为调查阈值，分析 iovec/链表开销、页粒度浪费或回收过激。5% 是预先设定的工程检查线，不是统计显著性判据；结果噪声大时先提高测试可信度。

若 O 只在连接轮换或背压场景获益，就限定适用范围。

## 9. 2026-11-09 No-delay off 实测结果

本节记录服务端未启用 TCP_NODELAY 的首次实验。后续开启结果及四种组合的并列比较见第 10 节。

### 9.1 结论摘要

**当前 O 已显著改善长连接历史峰值带来的内存保留，并降低多连接大回复的单位请求 CPU 开销。同时，当前默认 TCP 行为下出现了严重的大回复尾延迟退化，端到端性能需要按场景判断。**

- 256 个连接轮流读取 1 MiB、每组并发 16 时，15 秒后的 RSS 从 B0 的 262.48 MiB 降至 O 的 4.80 MiB，降低约 98.2%。连接在整个观察期保持存活。
- 1 MiB、8 连接时，服务端 CPU 从 312.05 μs/请求降至 147.09 μs/请求，降低约 52.9%。吞吐中位数提高 5.9%，完整回复 p99 却从 2.69 ms 上升至 41.73 ms。
- 单连接 1 MiB 的吞吐下降 81.4%，完整回复 p99 达到 46.75 ms。64 KiB × 16 pipeline 的单连接场景也出现同类退化。
- 单独的客户端 QUICKACK 对照中，O 的 40 ms 级尾部停顿消失，单连接大回复吞吐达到 B0 的约 2.28–2.34 倍。这支持 TCP 确认时序参与退化的判断。
- 小回复吞吐变化约为 +0.4% 至 -4.8%。当前数据没有显示普遍的小回复吞吐收益。

本轮实际执行口径如下。

1. 吞吐采用自建 C++ epoll 客户端，每个连接始终只有一批在途请求，最多 4 个客户端线程。每次接收最多读取 64 KiB，并逐字节校验整批 RESP 回复。延迟从开始发送该批请求算到完整收齐该批回复，P=1 是完整请求延迟，P>1 是整批延迟。
2. 每组运行 5 个独立重复，版本顺序交错。以 B0 校准约 5 秒所需请求数，两版本使用相同请求总数，预热请求数为正式请求数的一半。实际耗时随版本变化，原始 JSON 中记录 wall_s。正式吞吐共完成 **346,122,220 条请求**，客户端完整性检查全部通过。
3. 内存场景每组 5 轮、每轮全新进程。建立 256 个连接并预热 5 秒，分组读取大回复，全部收齐后用小请求完成排空屏障，再观察 15 秒。RSS 来自 smaps_rollup，每 250 ms 采样，并在每组突发完成时采样。表中峰值为采样峰值，VmHWM 原始值也已保存。
4. 固定到达率场景为 64 个正常连接、合计 5000 请求/秒、持续 20 秒。慢读场景额外加入 4 个连接，每批 3 条 1 MiB GET，约 1 MiB/s 读取，接收缓冲设置为 4096 B，asyncio 读取缓冲上限为 32 KiB。两版本使用相同设置。保存计划发送、实际发送、完整回复三个时间口径，直方图分辨率为 1 μs。
5. 再次突发场景每个间隔执行一组新进程序列，含初始轮及之后 10 个周期，16 个连接同时读取 1 MiB，每周期首批之后再读取 4 批。此项用于探索回收代价，独立重复数为 1，每个间隔的首批统计有 160 个样本。
6. S5 池机制探针、源码计数和 ACK 对照单独运行。主表使用原始二进制和默认 ACK 行为。实验环境仍受宿主机与容器其他进程影响。

试跑复用了 redis-benchmark，但其大回复延迟输出与完整收包口径存在差异，单线程客户端也在小回复场景接近满核。试跑结果保存在 `pilot-redis-benchmark/`，主表采用之后的 C++ 客户端结果。一次强制终止预热客户端曾触发 B0 的连接重置退出，随后改用完整排空的有限请求预热，正式轮次均独立重启服务端。

### 9.7 40 ms 尾部停顿的 ACK 对照

额外构建同一个 C++ 客户端，在每次成功 recv 后设置 TCP_QUICKACK。服务端仍运行同一组 B0/O 二进制，单连接，每组 5 个重复。该设置会改变 ACK 行为，因此这组结果用于诊断，与默认设置主表分别报告。

| 场景 | B0 QPS | O QPS | 吞吐倍数 | B0 完整回复/批次 p99 ms | O 完整回复/批次 p99 ms |
|---|---:|---:|---:|---:|---:|
| 1 MiB，P=1 | 3,594 | 8,201 | 2.28× | 0.3583 | 0.1480 |
| 64 KiB，P=16 | 54,551 | 127,875 | 2.34× | 0.3560 | 0.1507 |

两版本均采用该客户端设置后，O 的 40 ms 级停顿消失，池减少搬移的收益得以体现。结合服务端尚未设置 TCP_NODELAY、64 KiB 发送预算后可能留下很短的 RESP 尾部，结果支持“发送分段时序、Nagle 与延迟 ACK 交互”这一解释。此结论来自受控 ACK 对照，具体逐包行为仍有待抓包确认。TCP_QUICKACK 的状态会随协议处理变化，因此诊断在每次读取后重新设置。[Linux tcp(7)](https://man7.org/linux/man-pages/man7/tcp.7.html)

## 10. TCP_NODELAY on/off 完整对照

### 10.1 改动、版本与方法

2026-11-09 在 `Server::accept_connections()` 的每条新接受客户端 socket 上设置 `TCP_NODELAY=1`，成功后进入原有的非阻塞配置和事件注册流程。设置失败时关闭该 socket 并抛出系统错误。B0 从固定提交的临时源码目录构建，应用与当前 O 相同的 [nodelay.patch](./scripts/nodelay.patch)。

两份新服务端产物均由各自源码目录中的 `build.sh` 编译，使用原有 `-std=c++17 -O2 -DNDEBUG -Wall -Wextra -Werror` 参数。再次通过 `build.sh` 构建后，`cmp` 校验两份产物逐字节一致。

| 版本 | 服务端 No-delay off | 服务端 No-delay on |
|---|---|---|
| B0 | `redlet-64kb-buffer` | `redlet-64kb-buffer-nodelay` |
| O | `redlet-chunk-pool` | `redlet-chunk-pool-nodelay` |

新产物的 SHA-256 如下。

| 产物 | SHA-256 |
| --- | --- |
| redlet-64kb-buffer-nodelay | `8d4933df71f2661b80b476e60c5417b725caae7041a4442adfb467544a378252` |
| redlet-chunk-pool-nodelay | `885886d2c50d521921d4dea319ad792f53e51b2805751fdeba3e29e7c0d1ec26` |

No-delay off 取第 9 节的上一轮完整数据，No-delay on 为本轮重新运行的数据。两轮使用同一 Linux 开发容器、CPU 绑定、数据集、发送预算、连接数和池参数。每个模式内的 B0/O 交替运行，每次启动新服务端。吞吐请求数依照各轮 B0 校准到约 5 秒，再给同组 O 使用相同请求数。主测试客户端采用原有 ACK 行为，额外 QUICKACK 对照单独运行。

两种 No-delay 模式按先后两轮采样，跨模式的小幅差异会受时间和虚拟机运行波动影响。同一模式内交替采样的 B0/O 比较用于评价池的收益。以下吞吐、内存、混合负载和 ACK 表使用 5 次运行的中位数。周期突发每个间隔各运行一个独立序列，排除初始轮后统计 10 次突发。

## 11. 两轮实验结论

### 11.1 已观察到的收益与退化

**ChunkPool 在长连接轮换、大回复输出和空闲回收场景中产生了明确收益。双方开启 TCP_NODELAY 后，大回复的吞吐、服务端 CPU 成本和 p99 同时改善，小回复的多连接及 pipeline 场景仍有退化。**

以下性能差值采用双方均开启 TCP_NODELAY 时的 B0/O 对照，数值为 5 次运行的中位数。

| 维度 | 实测结果 | 结论 |
|---|---|---|
| 大回复吞吐 | 四组 64 KiB / 1 MiB 负载中，O 为 B0 的 2.39–2.51 倍 | 大回复吞吐显著提升 |
| 大回复 CPU | 单请求服务端 CPU 时间下降约 58%–65% | 输出路径的计算成本显著降低 |
| 大回复 p99 | 相对 B0 下降约 51%–61% | 大回复完整接收或整批接收的尾延迟改善 |
| 小回复吞吐 | C1/P1 基本持平，C64/P1 下降 2.7%，C256/P1 下降 6.4%，C8/P32 下降 14.7% | 多连接和 pipeline 小回复承担额外开销 |
| 小回复 pipeline p99 | C8/P32 从 0.0550 ms 增至 0.1468 ms，约为 B0 的 2.67 倍 | 该场景存在额外尾部抖动 |
| 长连接空闲 RSS | 每组 16 条连接时，从约 262.48 MiB 降至 4.80–4.83 MiB；每组 64 条时降至 16.31 MiB | 排空后 15 秒的 RSS 分别降低约 98.2% 和 93.8% |

内存收益在 No-delay off/on 两轮均成立。Chunk 跨连接复用降低轮换突发的峰值，页回收与整 Slab 回收进一步降低空闲 RSS。每组 16 条连接约在排空后 11.25 秒释放 90% 的突发额外 RSS，每组 64 条在 15 秒时仍受回收节奏影响。

### 11.2 性能变化的机制解释

**输出前缀搬移的消除有直接计数支持。** B0 发送总计 256 MiB payload 时，累计搬移约 1.875 GiB，为 payload 的 7.5 倍，No-delay off/on 两轮结果一致。O 通过推进 Chunk 游标消费输出，消除了这一项搬移。该机制与大回复服务端 CPU 成本降低的测量结果一致。

**物理页回收有独立探针支持。** 32 个 Slab 各保留一个 InUse Chunk 时，32 MiB 映射持续存在，回收后驻留页为 96，包含 32 个活页和 64 个 Warm 页，活页数据校验通过。Cold/Warm 分离实现了部分活跃 Slab 内空闲页的物理内存回收。

**TCP 开关显著影响端到端结果。** No-delay off 时，O 的四组大回复 p99 为约 40–47 ms；开启后分别降至约 0.147、1.195、0.149、1.336 ms。结合客户端 QUICKACK 对照，结果支持 Nagle、延迟 ACK 与分段发送相互影响的解释，具体报文时序仍缺少抓包验证。池的性能收益采用同一 TCP 设置下的 B0/O 比较，O 自身从 off 到 on 的提升还包含 TCP 开关收益。

### 11.3 成本与结论边界

- 小回复的额外 CPU 成本和尾部抖动已经出现在数据中，具体开销分布仍需 profiling 确定。
- 回收后复用会重新触页。No-delay on 的 5 秒和 11 秒间隔突发，首批 minor faults 中位数分别为 746 和 3,351.5。周期突发每个间隔仅运行一个独立序列，延迟结果用于描述本轮表现。
- 维护配置中的 200 μs 是软预算，独立服务端诊断记录到单次维护最高 876 μs。
- 慢客户端场景中，实际发送至完成的 p99 从 1.198 ms 降至 0.975 ms；计入客户端调度等待后，从 3.409 ms 降至 3.375 ms。毫秒级客户端调度波动限制了公平性结论的强度。
- No-delay off/on 按先后两轮采样，跨模式的小幅变化受运行波动影响。透明大页也影响部分内存样本，详细表格保留中位数和异常范围。
- 本轮 350,064,770 个吞吐测试回复均完成校验，全部实验记录零客户端错误，8 项正确性测试通过，正确性结论覆盖这些已执行场景。

综合两轮结果，当前实现适合本实验设定的回复大小波动、偶发大回复且连接长期存活的场景。主要成果是跨连接复用与物理内存回收，以及开启 TCP_NODELAY 后的大回复输出效率提升。小回复管理开销、重新触页成本和维护软预算超时构成当前实现的取舍。
